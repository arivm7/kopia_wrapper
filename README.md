# Kopia Backup Scripts

Обёртка для [kopia](https://kopia.io) — набора bash-скриптов для резервного копирования и восстановления системных каталогов и файлов через [kopia](https://kopia.io) — быстрый, шифрующий, дедуплицирующий инструмент резервного копирования с открытым исходным кодом.

**Версия:** 2.0.0 (2026-10-30)

## Состав проекта

| Файл | Назначение |
|---|---|
| `kopia_common.sh` | Общая библиотека: пути, настройки, служебные функции. Не запускается самостоятельно, только подключается через `source`. |
| `kopia_backup.sh` | Создаёт снапшоты всех настроенных путей, применяет политику хранения и сохраняет restore-kit. |
| `kopia_restore_to.sh` | Восстанавливает последние снапшоты всех путей в отдельную папку с сохранением структуры; умеет показывать информацию об архиве (`--info`), список снапшотов (`--list`), манифест (`--manifest`) и монтировать репозиторий (`--mount`). |
| `install.sh` | Копирует все файлы проекта в выбранную папку, настраивает права и подключает автодополнение. |
| `kopia-completion.bash` | Автодополнение bash (только имена флагов) для `kopia_backup.sh` и `kopia_restore_to.sh`. |

Все файлы должны находиться в одном каталоге — `kopia_backup.sh`, `kopia_restore_to.sh` и `install.sh` подключают `kopia_common.sh` из своей директории через `source "${APP_DIR}/kopia_common.sh"`.

## 1. `kopia_common.sh` — общая библиотека

### 1.1. Определение путей

Все пути привязаны к домашнему каталогу пользователя, который **реально** запустил скрипт, а не к тому, во что превращается `$HOME` после `sudo`:

```bash
if [[ -n "${SUDO_USER:-}" ]]; then
    REAL_HOME="$(getent passwd "$SUDO_USER" | cut -d: -f6)"
else
    REAL_HOME="$HOME"
fi
```

SUDO_USER всегда содержит имя исходного пользователя (устанавливается самим sudo), поэтому REAL_HOME остаётся стабильным независимо от того, была ли эскалация прав.

На основе REAL_HOME строятся все рабочие пути:

| Переменная | Путь | Назначение
|---|---|
| `CONFIG_PATH` | $REAL_HOME/.config/kopia_backup/ | Каталог с пользовательскими настройками |
| `CONFIG_FILE` | $CONFIG_PATH/kopia_common.conf | Единый конфиг, общий для `kopia_backup.sh` и `kopia_restore_to.sh` (имя берётся от `kopia_common.sh`, а не от вызывающего скрипта) |
| `REPO_PATH` | $REAL_HOME/Backups/kopia_backup/<hostname> | Физическое хранилище данных репозитория `kopia` (подпапка с именем хоста — удобно, если один и тот же конфиг когда-нибудь окажется скопирован на другую машину) |
| `KOPIA_CONFIG` | $CONFIG_PATH/repository.config | Файл подключения kopia к репозиторию |
| `KOPIA_PASSWORD_FILE` | $CONFIG_PATH/.kopia_pass | Пароль репозитория в открытом виде (для неинтерактивного запуска) |
| `KOPIA_PATHS_FILE` | $CONFIG_PATH/source_paths.txt | Список путей, которые бэкапятся (генерируется автоматически из `SOURCE_PATHS`) |
| `RESTORE_ROOT_DEFAULT` | $REAL_HOME/Backups/kopia_restore/<метка_времени> | Папка восстановления по умолчанию |
| `EDITOR` | `nano` (по умолчанию) | Редактор, используемый ключом `-ec`/`--edit_config`. Может быть именем команды в `PATH` (`nano`, `vim`, `vi`, `kate`, `emacs`) или полным путём к исполняемому файлу (`/usr/bin/nano`). Задаётся в секции CONFIG `kopia_common.sh`. |

### 1.2. SOURCE_PATHS — что бэкапится

Массив путей (каталогов и/или отдельных файлов), которые попадают в резервную копию:
```bash

SOURCE_PATHS=(
    "/etc"
    "/var/www"
    "/var/spool/cron"
    "/home"
    "/root"
)
```

kopia одинаково умеет создавать снапшоты как каталогов, так и отдельных файлов — можно смешивать оба типа в списке.

### 1.3. Исключения (.kopiaignore)

Для исключения подпапок/файлов из бэкапа конкретного пути используется файл `.kopiaignore` внутри самого этого каталога (синтаксис как в `.gitignore`):

```text
cache/
tmp/
*.log
node_modules/
!important.log
```

Автоматического применения исключений через код в скриптах нет — это делается вручную, кладя .kopiaignore в нужные каталоги.

### 1.4. Механизм пользовательского конфига

При первом запуске `kopia_backup.sh` вызывается `read_config_file()`:

- Если `$CONFIG_FILE` уже существует — он подключается через `source`, и значения переменных (`REPO_PATH`, `SOURCE_PATHS` и т.д.) переопределяются из него.
- Если файла ещё нет — вызывается `save_config_file()`, которая:
  1. Извлекает через `awk` фрагмент `kopia_common.sh` между маркерами `[CONFIG START]` и `[CONFIG END]` (это блок с `REPO_PATH`, `KOPIA_CONFIG`, `KOPIA_PASSWORD_FILE`, `RESTORE_ROOT_DEFAULT`, `SOURCE_PATHS`, `RESTORE_KIT_MODE` и комментарием про `.kopiaignore`).
  2. Сохраняет этот фрагмент как есть в `$CONFIG_FILE` (`~/.config/kopia_backup/kopia_common.conf` — **один файл на оба скрипта**).
  3. Выводит сообщение с предложением отредактировать конфиг и запустить скрипт заново, после чего завершает работу (`exit 0`).

Это выполняется **до** эскалации прав (`require_root`), поэтому файл создаётся и остаётся собственностью обычного пользователя — редактировать его можно без `sudo`.

Для редактирования конфига без запуска бэкапа предусмотрен ключ
`-ec`/`--edit_config` (см. ниже, разделы 2 и 3). Он открывает
`$CONFIG_FILE` в редакторе, указанном в переменной `EDITOR` секции
CONFIG (`nano` по умолчанию), **от имени пользователя, не от root** —
конфиг принадлежит реальному пользователю, и редактировать его
root-редактором не нужно (и вредно: файл может сменить владельца
или остаться с root-окружением).

Если конфига ещё нет, `-ec` сначала вызовет `save_config_file()`,
которая создаст **шаблон** конфига (с дефолтными путями, не
отражающими реальную структуру текущей системы) и **завершит скрипт**
с сообщением «отредактируйте и запустите заново». Это сделано
намеренно: пользователь должен осознанно пройти через редактирование,
а не запустить бэкап с дефолтными путями, которые могут оказаться
неверными. После этого нужно запустить `-ec` ещё раз — теперь конфиг
существует, и он откроется в редакторе.

После чтения конфига `kopia_backup.sh` вызывает `write_source_paths_file()` — обновляет `$KOPIA_PATHS_FILE` (source_paths.txt) из текущего массива `SOURCE_PATHS`, но только если он изменился (сравнение через `read_source_paths_file`).

### 1.5. Restore-kit

Restore-kit — набор файлов, достаточный для восстановления архива на другой машине без ручного ввода пароля. Сохраняется рядом с репозиторием при каждом запуске `kopia_backup.sh`.

Куда именно класть restore-kit, задаётся переменной `RESTORE_KIT_MODE`:

| Значение | Путь | Описание |
|---|---|---|
| `in` (по умолчанию) | `$REPO_PATH/restore_kit/` | Всё в одном месте |
| `out` | `${REPO_PATH}.restore_kit/` | Рядом, но отдельно — можно увезти на другой носитель |
| `none` | — | Не сохранять |

Состав restore-kit (`RESTORE_KIT_FILES`):
- `repository.config` — файл подключения к репозиторию
- `repository.config.kopia-password` — пароль репозитория (base64-обфускация)
- `.kopia_pass` — тот же пароль в открытом виде
- `source_paths.txt` — список путей, которые бэкапятся
- `README.txt` — инструкция по восстановлению (генерируется автоматически, перезаписывается только при смене версии)

**ВНИМАНИЕ:** restore-kit содержит пароль репозитория. Храните его так же тщательно, как сами данные.

### 1.6. Проверка и установка зависимостей

```bash
REQUIRED_PACKAGES=(
    "kopia:"   # без apt-пакета — устанавливается вручную по инструкции с kopia.io
    "jq:jq"    # доступен через apt
)
```

Формат: "команда:apt_пакет". check_required_packages():

    для программ без apt-пакета (пустая часть после :) — при отсутствии сразу выводит ошибку и завершает скрипт (exit 1), автоустановка не предлагается;

    для программ с apt-пакетом — при отсутствии спрашивает разрешение на apt-get install -y; при отказе или ошибке установки — тоже exit 1.

### 1.7. Проверка файла пароля

`check_kopia_password_file()` проверяет, что `$KOPIA_PASSWORD_FILE`:
1. существует;
2. имеет права доступа `600`.

При несоответствии — понятная ошибка с инструкцией по исправлению и `exit 1`.

### 1.8. Самоповышение прав (`require_root`)

```bash
require_root() {
    if [[ "$(id -u)" -eq 0 ]]; then
        return 0
    fi
    exec sudo -- "$0" "$@"
    ...
}
```

Если скрипт запущен не от root — он перезапускает сам себя через sudo с теми же аргументами командной строки (exec полностью замещает текущий процесс). Благодаря этому:

    вручную вызывать sudo не нужно — достаточно запустить скрипт как обычный пользователь;

    все операции после require_root (чтение /etc, создание снапшотов и т.д.) выполняются от root;

    справка (--help/--usage) и версия (--version) отрабатывают без запроса пароля sudo, так как вызываются до require_root.

### 1.9. Прочие функции

| Функция | Назначение |
|---|---|
| `log_info / log_error` | Обёртки над logger — пишут сообщения в системный журнал с префиксом BACKUPER. |
| `exit_with_msg "текст" код/префикс` | Единая точка вывода сообщения (с цветом в терминале) + запись в лог + exit. Код `0` — успех, `1` — ошибка, `2` — ошибка с подсказкой по `--usage`, `другое` — info префикс информационного сообщения. |
| `print_version` | Печатает имя скрипта, заголовок, версию, историю изменений и copyright. |
| `write_source_paths_file` | Обновляет source_paths.txt из SOURCE_PATHS (только при изменении). |
| `read_source_paths_file` | Читает source_paths.txt в глобальный массив SOURCE_PATHS_FROM_FILE. |
| `write_restore_kit` | Создаёт/обновляет restore-kit рядом с репозиторием. |
| `edit_config_file` | Открывает `$CONFIG_FILE` в редакторе из `$EDITOR` (секция CONFIG). Проверяет наличие редактора: для `nano` при отсутствии предлагает установить через apt; для остальных — ошибка с подсказкой. Выполняется **до** `require_root` (от имени пользователя). Если конфига нет — вызывает `save_config_file` (создаёт шаблон и завершает скрипт). |

## 2. kopia_backup.sh — резервное копирование

Ключи командной строки

### Ключи командной строки

```text
kopia_backup.sh [-H|--help] [-u|--usage] [-V|--version] [-ec|--edit_config]
```

| Ключ | Действие |
|---|---|
| -H, --help | Полная справка |
| -u, --usage | Краткая строка использования |
| -V, --version | Версия скрипта |
| -ec, --edit_config | Открыть конфиг-файл обёртки ($CONFIG_FILE) в редакторе из $EDITOR и выйти. Редактирование выполняется от имени пользователя, не от root. Если конфига ещё нет — создаётся шаблон и скрипт завершается с сообщением «запустите заново». После редактирования нужно запустить скрипт заново, чтобы применить изменения. |

Позиционных аргументов скрипт не принимает.

### Порядок выполнения

1. Разбор `-H`/`-u`/`-V` и `-ec`/`--edit_config` (если указаны — вывод и выход, без root). `-ec` обрабатывается **до** `read_config_file`: если конфига нет, создаётся шаблон и скрипт завершается; если есть — открывается редактор, и после редактирования скрипт выходит с сообщением «запустите заново».
2. `read_config_file` — чтение/создание пользовательского конфига (без root).
3. `write_source_paths_file` — обновление `source_paths.txt` из `SOURCE_PATHS`.
4. Вывод диагностической информации: путь к репозиторию (`REPO_PATH`), конфиг-файл обёртки (`CONFIG_FILE`), конфиг kopia (`KOPIA_CONFIG`), список путей (`KOPIA_PATHS_FILE`).
5. `require_root "$@"` — самоповышение прав через `sudo`, если нужно.
6. `check_required_packages` — проверка/установка `kopia`, `jq`.
7. `check_kopia_password_file` — проверка файла пароля.
8. Подключение к существующему репозиторию (`kopia repository connect`) или создание нового (`kopia repository create`), если он ещё не инициализирован по `$REPO_PATH`.
9. `write_restore_kit "$REPO_PATH"` — сохранение restore-kit рядом с репозиторием.
10. Цикл по `SOURCE_PATHS`:
    - `kopia snapshot create "$DIR"` — создание снапшота;
    - `kopia policy set "$DIR" --keep-daily 30 --keep-weekly 12 --keep-monthly 12` — политика хранения (30 суточных / 12 недельных / 12 месячных снапшотов).
    - Пути, которые не существуют на диске, пропускаются с предупреждением, а не обрывают весь скрипт.
11. `kopia maintenance run` — лёгкое обслуживание репозитория.
    Полное обслуживание (`--full`) в скрипт **намеренно не входит** — его рекомендуется запускать отдельным cron-заданием раз в неделю:
```bash
    kopia maintenance run --config-file "$KOPIA_CONFIG" --full
```

    Если хотя бы один путь завершился с ошибкой — скрипт завершается с кодом 1 и списком проблемных путей; иначе — exit 0.

Все вызовы kopia явно используют --config-file "$KOPIA_CONFIG", чтобы гарантированно работать с нашим репозиторием, а не с конфигом kopia по умолчанию.

## 3. kopia_restore_to.sh — восстановление

Ключи и аргументы
```text

kopia_restore_to.sh --repo <архив> [ОПЦИИ]
kopia_restore_to.sh --repo <архив> [--password-file <файл>] [-i|--info [ПУТЬ]]
kopia_restore_to.sh -ec|--edit_config
kopia_restore_to.sh -H|--help | -V|--version
```

| Аргумент | Описание |
|---|---|
| `--repo <путь>` Обязательный. | Путь к каталогу репозитория kopia (архив). |
| `--to <путь>` | Каталог, в который восстановить все пути из source_paths.txt (режим автоматического восстановления). |
| `--password-file <файл>` | Файл с паролем репозитория (chmod 600). Обязателен, если restore-kit не найден. |
| `--kit <путь>` | Явно указать каталог restore-kit. |
| `-i`, `--info [ПУТЬ]` | Показать информацию об архиве и выйти. Без ПУТИ — сводка по всем путям из source_paths.txt. С ПУТЬЮ — то же плюс список файлов/папок верхнего уровня (kopia ls). |
| `--list` | Показать список всех снапшотов в репозитории (kopia snapshot list --all). |
| `--manifest` | Показать манифест репозитория (kopia manifest list). |
| `--mount <точка>` | Примонтировать весь репозиторий для ручного копирования. Блокируется до Ctrl-C. |
| `-ec`, `--edit_config` | Открыть конфиг-файл обёртки (`$CONFIG_FILE`) в редакторе из `$EDITOR` и выйти. Редактирование выполняется **от имени пользователя, не от root**. Не требует `--repo`. Если конфига ещё нет — создаётся шаблон и скрипт завершается. После редактирования нужно запустить скрипт заново. |
| `-H`, `--help` | Показать справку. |
| `-V`, `--version` | Показать версию. |

Ключи `--list`, `--manifest`, `--mount` и `--info` взаимоисключающие.

### Режимы работы

**Режим 1 — автоматическое восстановление (restore-kit найден):**
```bash
kopia_restore_to.sh --repo /mnt/usb/archive --to /mnt/restore
```

Скрипт находит restore-kit (внутри репозитория или рядом), подключается по repository.config из него, берёт пароль из .kopia_pass, читает список путей из source_paths.txt и восстанавливает все пути в указанный каталог с сохранением структуры.

Режим 2 — работа без restore-kit (старый/чужой архив):
```bash

kopia_restore_to.sh --repo /mnt/usb/archive --password-file /root/.pass --list
kopia_restore_to.sh --repo /mnt/usb/archive --password-file /root/.pass --manifest
kopia_restore_to.sh --repo /mnt/usb/archive --password-file /root/.pass --mount /mnt/view
```

Скрипт подключается к репозиторию и показывает его содержимое либо монтирует для ручного копирования. Решение о том, что извлекать, принимает администратор.

Порядок выполнения

1. Разбор аргументов. `-ec`/`--edit_config` обрабатывается в общем цикле и **не требует** `--repo` — при его наличии вызывается `edit_config_file` и скрипт выходит. Для остальных действий проверяется обязательный `--repo` и существование репозитория.

2. require_root "${ORIG_ARGS[@]}" — самоповышение прав.

3. Создание временного каталога (mktemp -d) для repository.config, чтобы не пересекаться с локальным конфигом kopia. Временный каталог удаляется по trap EXIT.

4. check_required_packages.

5. Поиск restore-kit (приоритет: --kit, <repo>/restore_kit/, <repo>.restore_kit/).

6. Определение KOPIA_PASSWORD_FILE (из restore-kit или --password-file).

7. check_kopia_password_file.

8. Подключение к репозиторию.

9. Выполнение запрошенного действия (--info, --list, --manifest, --mount) или автоматическое восстановление.

10. При автоматическом восстановлении: чтение source_paths.txt, защита от перезаписи непустого каталога (y/N), цикл по путям с поиском самого свежего снапшота:

```bash
kopia snapshot list "$SRC" --config-file "$KOPIA_CONFIG" --json \
    | jq -r 'max_by(.startTime) | .id // empty'
```

    max_by(.startTime) выбирает запись с максимальным временем начала снапшота.

    Восстановление в ${TO_ARG}${SRC} (структура путей сохраняется).

    Итог — список путей, которые не удалось восстановить (если такие есть), и код выхода 1; иначе exit 0.

Восстановление всегда идёт в отдельную директорию, а не поверх оригинальных путей — это позволяет вручную сверить данные перед тем, как что-либо перезаписывать в рабочей системе.
Просмотр информации об архиве (--info)
```bash

kopia_restore_to.sh --repo /mnt/usb/archive -i
kopia_restore_to.sh --repo /mnt/usb/archive -i /etc
```

Источники данных, которые использует print_archive_info():

    дата последнего снапшота — поле startTime из kopia snapshot list --json;

    размер/файлы/папки — поля rootEntry.summ.size/rootEntry.summ.files/rootEntry.summ.dirs;

    листинг верхнего уровня — kopia ls <ID> (не рекурсивно).

Размер выводится в человекочитаемом виде через numfmt --to=iec-i, с байтами в качестве резервного варианта.

## 4. Установка (`install.sh`) и автодополнение

Устанавливает `kopia_common.sh`, `kopia_backup.sh`, `kopia_restore_to.sh` и `kopia-completion.bash` в выбранную папку, настраивает права на выполнение и подключает автодополнение bash.

```bash
install.sh [-H|--help] [--usage] [-V|--version] [ПУТЬ_УСТАНОВКИ]

Целевая папка задаётся либо позиционным аргументом (любой произвольный путь), либо интерактивным меню, если аргумент не передан:

Выберите папку установки:

    /usr/bin/ (требуется root, не рекомендуется)

    $HOME/bin/ (рекомендуется, по умолчанию)

    $HOME/.local/bin/ (опционально)
    q) Отмена — прервать установку
    Ваш выбор (q|1|2|3) [2]:
```

- Пустой ввод (просто `Enter`) → вариант **2** (`$HOME/bin`) по умолчанию.
- `q` — прерывает установку сразу, не создавая ничего.
- Если целевая папка требует root (например, `/usr/bin`) — инсталлятор сам определяет это через реальную проверку прав на запись (не по жёсткому списку префиксов пути) и перезапускается через `sudo`, передавая уже выбранный путь явно, так что меню при этом повторно не показывается.

При переустановке в непустую папку с уже существующими файлами проекта запрашивается подтверждение:

```bash
Перезаписать существующие файлы? (q|y|n) [N]:
```

Пустой ввод → `N` (не перезаписывать, отмена), `q` — прервать установку с отдельным сообщением.

Устанавливаемые файлы и права:
- **Исполняемые** (`chmod +x`): `kopia_backup.sh`, `kopia_restore_to.sh`
- **Неисполняемые** (`chmod -x`): `kopia_common.sh`, `kopia-completion.bash`

### Автодополнение (`kopia-completion.bash`)

Дополняет только имена флагов (`--help`, `--usage`, `--version`, `-i`/`--info`, `-ec`/`--edit_config` и т.д.) — без подстановки конкретных путей. После флагов, требующих аргумент (`--repo`, `--to`, `--password-file`, `--kit`, `--mount`, `-i`/`--info`), работает стандартное файловое дополнение bash.

`install.sh` автоматически:
1. копирует файл в целевую папку вместе с остальными;
2. добавляет строку `source ".../kopia-completion.bash"` в `~/.bashrc` **реального** пользователя (даже если установка шла через `sudo` в `/usr/bin`);
3. перед добавлением проверяет, нет ли такой строки уже — повторные запуски инсталлятора не дублируют строку в `.bashrc`.

После установки нужно перелогиниться либо выполнить `source ~/.bashrc`, чтобы автодополнение заработало в текущей сессии.

## 5. Первоначальная настройка

```bash
# 1. Установить зависимости (или довериться автоматическому предложению скрипта)
sudo apt install jq
# kopia ставится по официальной инструкции: https://kopia.io/docs/installation/

# 2. Создать файл с паролем репозитория
mkdir -p ~/.config/kopia_backup
echo 'ваш-надёжный-пароль' > ~/.config/kopia_backup/.kopia_pass
chmod 600 ~/.config/kopia_backup/.kopia_pass

# 3. Первый запуск — создаст шаблон конфига и остановится
./kopia_backup.sh
# → отредактируйте ~/.config/kopia_backup/kopia_common.conf при необходимости
#   (пути SOURCE_PATHS, REPO_PATH, RESTORE_KIT_MODE и т.д.)
#   либо используйте встроенный ключ:
#   ./kopia_backup.sh -ec
#   (откроет конфиг в редакторе из EDITOR; работает от имени пользователя, не от root)

# 4. Повторный запуск — создаст репозиторий (если его ещё нет), снапшоты
#    и restore-kit
./kopia_backup.sh
```

Автоматизация через cron

```text

USER=user
HOME=/home/user
PATH=/usr/local/bin:/usr/bin:/bin:/home/user/bin:/home/user/.local/bin
SHELL=/bin/bash
BASH_ENV=/home/user/.bashrc

30 2 * * *   /path/to/kopia_backup.sh >>/var/log/kopia_backup.log 2>&1
0  4 * * 6   kopia maintenance run --config-file /home/USER/.config/kopia_backup/repository.config --full >>/var/log/kopia_backup.log 2>&1
```

Если крон-задание должно работать без пароля sudo, добавьте узкое правило в /etc/sudoers.d/:

```text
username ALL=(root) NOPASSWD: /path/to/kopia_backup.sh, /path/to/kopia_restore_to.sh
```

и убедитесь, что сами файлы .sh принадлежат root:root, а не пользователю — иначе пользователь сможет подменить содержимое скрипта, который выполняется через NOPASSWD.

## 6. Восстановление на другой машине

С restore-kit (рекомендуется)

    Установите kopia на новой машине.

    Скопируйте репозиторий (или смонтируйте носитель).

    Восстановите с помощью скрипта:

```bash

# restore-kit внутри репозитория (mode=in)
kopia_restore_to.sh --repo /путь/к/репозиторию --to /путь/для/восстановления

# restore-kit рядом (mode=out)
kopia_restore_to.sh \
    --repo /путь/к/репозиторию \
    --kit /путь/к/репозиторию.restore_kit \
    --to /путь/для/восстановления
```

Без restore-kit (вручную)

Если нужно поправить конфиг (например, путь к репозиторию или
`EDITOR`) перед восстановлением, используйте:

```bash
kopia_restore_to.sh -ec
```
Редактирование выполняется от имени пользователя, не от root.


Если restore-kit отсутствует, используйте режимы --list, --manifest и --mount:
```bash

# Посмотреть список снапшотов
kopia_restore_to.sh --repo /путь/к/репозиторию --password-file /root/.pass --list

# Примонтировать для ручного копирования
kopia_restore_to.sh --repo /путь/к/репозиторию --password-file /root/.pass --mount /mnt/view

# Посмотреть информацию о конкретном пути
kopia_restore_to.sh --repo /путь/к/репозиторию --password-file /root/.pass -i /etc
```

### Ручное восстановление голыми командами kopia

Если система полностью потеряна и есть только хранилище репозитория и пароль:

```bash
# 1. Подключиться к существующему репозиторию (НЕ create!)
kopia repository connect filesystem --path /путь/к/kopia_backup

# 2. Проверить подключение
kopia repository status

# 3. Посмотреть список путей
kopia snapshot list

# 4. Найти снапшот конкретного пути
kopia snapshot list /etc

# 5. Восстановить в отдельную папку
mkdir -p /mnt/restore
kopia snapshot restore <ID_снапшота> /mnt/restore/etc

# 6. Массовое восстановление всех путей
for SRC in /etc /var/www /var/spool/cron /home /root; do
    ID=$(kopia snapshot list "$SRC" --json | jq -r 'max_by(.startTime) | .id // empty')
    [[ -n "$ID" ]] && kopia snapshot restore "$ID" "/mnt/restore${SRC}"
done
```

## 7. Известные особенности

    - kopia snapshot list <путь> может вернуть снапшоты родительских каталогов, если они тоже бэкапятся отдельно и вложены друг в друга (см. kopia#2659). В текущем SOURCE_PATHS вложенных путей нет, но при добавлении новых стоит проверять, не оказался ли один путь внутри другого.

    - Конфиг-файл (CONFIG_FILE) единый для обоих скриптов (kopia_common.conf) — изменения SOURCE_PATHS/REPO_PATH достаточно внести один раз.

    - Все вызовы kopia в скриптах используют явный --config-file, чтобы не зависеть от конфига kopia по умолчанию.

    - kopia_restore_to.sh всегда использует временный repository.config (mktemp -d), который удаляется по trap EXIT — это исключает конфликт между локальным и внешним репозиторием.

    - Restore-kit содержит пароль репозитория в открытом виде (.kopia_pass) и в base64-обфускации (repository.config.kopia-password). Это не шифрование — храните restore-kit так же тщательно, как сами данные.

    - **Редактирование конфига (`-ec`/`--edit_config`) выполняется от имени пользователя, не от root.** Это важно: конфиг принадлежит реальному пользователю (`$REAL_HOME/.config/kopia_backup/`), и запуск редактора через `sudo` мог бы сменить владельца файла или оставить его с root-окружением. Поэтому `-ec` обрабатывается **до** `require_root` и не требует root-прав. Если конфига ещё нет, создаётся шаблон (с дефолтными путями, не отражающими реальную структуру системы) и скрипт завершается — это заставляет пользователя осознанно пройти через редактирование, а не запустить бэкап с неверными путями.
